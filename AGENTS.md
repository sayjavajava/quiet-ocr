# Working in this repo (for coding agents)

You are working on **QuietOCR** — browser OCR (image or PDF → text, `.docx`, or a searchable PDF)
in 12 languages, running entirely on the user's machine. This file tells you how work is done here.
It's aimed at coding agents (Claude Code, Cursor, Codex, and anything else that reads `AGENTS.md`),
but nothing in it is agent-specific — a human contributor should read it too.

**Read [`CONTRIBUTING.md`](CONTRIBUTING.md) as well.** It has the setup and the pre-PR checklist
and is not duplicated here.

---

## 1. The one thing you must not break

**Nothing the user opens is ever transmitted.** That's the whole value of the project, and
[`SECURITY.md`](SECURITY.md) treats a regression as a security boundary being crossed, not a
preference being violated.

`npm run verify` enforces it automatically on every PR, across **Chromium, Firefox and WebKit** in
a CI matrix. Do the manual version too, as `CONTRIBUTING.md` insists: load the page, run a real
image through it, and watch the Network tab — nothing beyond the initial same-origin `/vendor/`
load should ever be requested, no matter what you feed it. **If your change adds a network call of
any kind, that needs justifying explicitly in the PR description, not quietly merging.**

Note the deliberate distinction from its sibling
[OffGridPDF](https://github.com/sayjavajava/offline-pdf-utility): that one is a single file you can
run fully offline forever. This one is a served page. Don't blur the two claims — don't make this
one *pretend* to be offline the way that one actually is.

## 2. Setup and the gate

```bash
npm install
npm run serve    # builds public/vendor/, serves public/ at http://localhost:8080
npm run verify   # the test suite
```

`public/vendor/` is generated from installed npm packages by `scripts/copy-vendor-assets.mjs`.
Gitignored. Never commit it, never hand-edit it.

**`scripts/verify.mjs` *is* the test suite** — Playwright driving the real built page. There is no
unit-test layer, on purpose: the things that break here (canvas rendering, workers, OCR accuracy,
file downloads) can't be faked in jsdom. Add cases there.

## 3. How work is done here

### Verify against reality, not plausibility

This project is the strongest expression of that rule — its entire test strategy is "drive the real
page in a real browser".

- **Actually run an image through it.** A change that only compiles has demonstrated neither that
  OCR works nor that nothing was uploaded.
- **Accuracy thresholds come from measurement, not from hope.** `npm run measure-accuracy` produces
  the real per-language numbers; thresholds are set from those runs against both clean and degraded
  fixtures. When a language does badly on degraded input, **the honest move is to say so** — that's
  why the app shows an in-UI accuracy hint for the four weakest languages rather than hiding the
  weakness.
- **Don't quote a timing you didn't run.** `npm run bench` and `measure-render-scaling` exist for
  this.

A spike that proves an idea *doesn't* work is a success. Write down the real blocker and stop.

### Report honestly, including what you didn't do

PR descriptions here state what was verified, what was assumed, and what was deliberately skipped
and why — including a **"Not touched, and why"** section when that's the honest answer. Real
example of the standard: a commit in this project's history exists purely to correct an earlier
write-up that had called a real bug "expected behaviour".

### One concern per PR, driven to green

Branch (`claude/<topic>`) → implement → `npm run build && npm run verify` (twice, to catch
flakiness) → push → open PR → **watch CI to green** → address review → merge. A PR you opened is
yours until it merges or closes; red CI on it is work now. Never skip, disable, or quarantine a
test to get green. Remember CI runs three browsers — a pass locally on Chromium is one third of the
evidence.

### Comment the *why*, not the *what*

Comments here explain decisions, rejected alternatives, and constraints — not what the line already
says. If you make a non-obvious choice, the comment explaining it is part of the change.

## 4. Repo conventions

- **Plain HTML/CSS/JS in `public/`. No framework, no bundler**, no build step beyond copying vendor
  assets. This is a deliberate constraint, not an accident of history — keep it that way.
- **Language assets are vendored**, not fetched at runtime. Adding a language means adding its
  trained-data package, a fixture, a manifest entry, a measured accuracy threshold, and a
  `verify.mjs` case — not just a dropdown option.
- **Fixtures** are generated by `scripts/generate-test-fixture.mjs`, in clean and degraded variants
  per language.
- Backlog items are numbered `F-<n>`, tracked in the private `tool-docs` repo (§5). Numbers are
  never reused.

## 5. Where the deeper context lives

The backlog and planning history live in a **separate private `tool-docs` repository**, not here —
this repo is code plus its own user-facing docs. If you have access, read `tool-docs/AGENTS.md`
first, then `tool-docs/quiet-ocr/BACKLOG.md`.

**If you don't have access**, this file plus `CONTRIBUTING.md`, `README.md` and `SECURITY.md` are
enough to work correctly here. You'll be missing the backlog, so: don't invent an `F-` number, and
ask before starting anything large.
